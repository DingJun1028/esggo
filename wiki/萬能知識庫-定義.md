# 萬能知識庫 — 定義 (Omni Knowledge Library)

> **Status:** 🟢 已正式定義 (v2.0.0-alpha)  
> **Origin:** OA-Team 萬能蜂群 / junaikey 成長層  
> **5T 適用:** Traceable / Trackable / Tangible / Transparent / Trustworthy

---

## 一、 定義總覽

**萬能知識庫 (Omni Knowledge Library)** 是一個由 `junaikey` 成長層驅動的**知識分身系統**，負責將分散於 `vault` 目錄下的知識結點（Markdown 文件）孵化為可追溯、可追蹤、可驗證的知識分身，並透過 4 階段機制（Hatch → Absorb → Feedback → Project）實現「零時差學習迴路」。

### 1.1 定位

> 萬能知識庫不是靜態文件庫，而是**活的知識生物群落**：每個知識結點孵化一個分身，分身跟隨知識點分類、標註正確/錯誤變體，湊齊完整內容，最終將型別投影回本體（canonical types）。知識沉澱從 L1 原始資料，遞進到 L5 組織智慧。

### 1.2 核心特徵

| 特徵 | 說明 |
|---|---|
| **Traceable** | 每個分身都有 `source_origin` 標籤，可回溯至原始知識結點 |
| **Trackable** | 完整的 lifecycle hooks：孵化 → 分類 → 吸收 → 投影 → 沉澱 |
| **Tangible** | 知識分身可在 wiki / UI / 代理間直接觸發使用 |
| **Transparent** | 所有分類標記（correct/incorrect）公開可查，無隱藏幻覺 |
| **Trustworthy** | 5T frontmatter 統一，分身投影經 `sync-vault-types.ts` 接 canonical，本體鎖定 `Object.freeze()` |

### 2.1 核心目錄結構

```
vault/
├── Agents/
│   └── context/
│       ├── .avatar-registry.json   ← 30 個註冊結點 (含 00-Index.md)
│       ├── .avatar-types.d.ts       ← 7 枚型別投影
│       └── 00-Index.md              ← 反饋 MOC (萬能知識分身迴路)
└── ... (全部知識.mkdir.md 文件)
```

### 2.2 註冊表 (.avatar-registry.json)

| 欄位 | 說明 |
|---|---|
| `id` | base64 壓縮後的結點識別碼 (12 字元) |
| `node` | 結點標題或 wikilink |
| `type` | `heading` 或 `wikilink` |
| `file` | 原始文件相對路徑 |
| `correct` | true = 正確變體, false = 錯誤變體 |
| `variant` | `correct` 或 `incorrect` |
| `absorbed` | true = 已吸收反饋 |
| `projected_to_ontology` | true = 已投影回本體 |

### 2.3 型別投影 (.avatar-types.d.ts)

7 枚型別投影，對應：

| 型別 | 用途 |
|---|---|
| `ISecondBrainNote` | 第二大腦筆記 |
| `ESGKnowledgeBase` | ESG 知識庫 |
| `5TProtocol` | 5T 誠信協議 |
| `30Matrix` | 30 人蜂群矩陣 |
| `SyncVaultTypes` | 錢包同步型別 |
| `KnowledgeAvatar` | 知識分身 |
| `SedimentationLevel` | 知識沉澱層級 |

## 三、 4 階段運作機制

### 3.1 Hatch — 孵化分身

1. 掃描 `vault` 目錄下所有 `*.md` 文件（排除 `AGENTS.md`）
2. 提取 `## 標題` 作為結點標題
3. 提取 `[[wikilink]]` 作為跨結點連結
4. 每個結點孵化一個分身

```
結點格式:
  - type: 'heading' | 'wikilink'
  - text: 結點標題或連結名稱
  - file: 來源文件路徑
```

### 3.2 Absorb — 分類變體

1. 每個分身跟隨知識點
2. 偵測「錯誤變體」信號：`誤`、`錯`、`反證`、`推翻`、`假說`、`myth`、`wrong`、`incorrect`、`deprecated`
3. 標記 `correct: true/false`、`variant: correct | incorrect`

> **設計原則**: 錯誤變體不被刪除，而是保留。因為「當下最完整」的知識包含錯誤與正確兩種變體，分身跟隨並標記。

### 3.3 Feedback — 反饋 MOC

1. 每個分身被標記 `absorbed: true`
2. 反饋記錄寫入 `00-Index.md` 的「萬能知識分身迴路」區塊：
   ```
   > 萬能知識分身迴路: N 結點孵化, M 已吸收反饋本體 (零時差)
   ```
3. 動態更新迴路統計。

### 3.4 Project — 投影本體

1. 萃取分身中的 TypeScript 型別宣告：
   ```typescript
   export type | interface | enum <TypeName>
   ```
2. 寫入 `.avatar-types.d.ts` 作為暫存片段
3. `sync-vault-types.ts` 自動將其接到 `shared/types.ts` 本體
4. 本體鎖定 `Object.freeze()`，確保不可變

## 四、 知識沉澱層級 (Sedimentation Levels)

| 層級 | 標籤 | 定義 | 狀態標記 |
|---|---|---|---|
| **L1** | 原始資料 (raw data) | 剛寫入，未消化 | `L1` |
| **L2** | 結構化 (structured) | 已加 tag，結構化 | `L2` |
| **L3** | 語意化 (semantic) | 已生成 vector，語意可搜尋 | `L3` |
| **L4** | 推理化 (inferred) | 已 cross-reference，邏輯連接 | `L4` |
| **L5** | 組織化 (organizational wisdom) | 已沉澱為組織智慧，跨專案通用 | `L5` |

### 沉澱路徑

```
L1 (原始) → L2 (構造) → L3 (語意) → L4 (推理) → L5 (組織智慧)
   │          │          │          │          │
   │          │          │          │          ▼
   │          │          │          │     可跨專案復用
   │          │          │          ▼
   │          │          │     推理性知識網
   │          │          ▼
   │          │     語意搜尋
   │          ▼
   │     結構化標籤
   ▼
  原始文件
```

## 五、 5T 誠信協議適用

| 5T 原則 | 實施方式 |
|---|---|
| **Traceable** | 所有分身都有 `source_origin`、`file`、`node` 可追溯 |
| **Trackable** | 完整 lifecycle: Hatch → Absorb → Feedback → Project → 沉澱 |
| **Tangible** | 知識分身可在 wiki / 代理間直接觸發 |
| **Transparent** | 所有 `correct/incorrect` 標記公開，無隱藏幻覺 |
| **Trustworthy** | 5T frontmatter 統一，本體 `Object.freeze()` 鎖定 |

### 5T Frontmatter 標準

所有知識結點應具有統一的 5T frontmatter：

```yaml
---
source_origin: string          # 原始起點
co_authors: string[]           # 共同作者
tag: string[]                  # 標籤
source: string                 # 來源
created: string                # 建立時間 (ISO 8601)
---
```
