# Supabase RLS Security Audit for Sunshine ESG

> Ensure your ESG data governance remains "Sunshine-grade" by auditing Row Level Security (RLS) using Continue CLI and the Supabase MCP.

  tables.

## Overview

In the JunAiKey system, the **Sunshine ESG** schema (`supabase-schema.sql`) relies heavily on RLS to ensure that editors can only modify data for their own organization units, while auditors maintain read-only access.

---

## Auditing the Governance Layer

### 🔍 Schema-Specific Audit

Use Continue CLI to verify that the policies in `supabase-schema.sql` are correctly implemented and haven't drifted.

**Prompt:**

```bash
"Audit the RLS policies for the Sunshine ESG schema. Specifically:
1. Verify that 'editor' roles can only INSERT into 'esg_readings' where org_unit_id matches their profile.
2. Check if any tables like 'emission_factors' are missing RLS (they should be read-only for most users).
3. Ensure the security_definer function 'get_my_claim' is not expoitable."
```

---

## Fixing Permission Issues

If you identify a gap (e.g., a new table without RLS), use the AI to generate a migration.

### 🛠️ Policy Generation Prompt

**Prompt:**

```bash
"I've added a new table 'audit_logs'. Generate a Supabase RLS migration that:
1. Enables RLS.
2. Allows 'admin' full access.
3. Allows 'auditor' select-only access.
4. Blocks all other roles.
Include rollback SQL."
```

## Automated Monitoring

The project includes a GitHub Action template (`.github/workflows/db-health.yml`) that you can enable to run these audits periodically.

### Verification Matrix

| Table           | RLS Status | Primary Policy Pattern  |
| :-------------- | :--------- | :---------------------- |
| `org_units`     | Enabled    | Read-all, Admin-write   |
| `user_profiles` | Enabled    | Read-self               |
| `esg_readings`  | Enabled    | Org-based isolation     |
| `esg_evidence`  | Enabled    | Inherited from readings |
